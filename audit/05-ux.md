## 3. Duplication `dashboard/assets` vs `dashboard/assets/fleet`

**Constaté** : ce n'est pas un doublon. Les deux vues divergent sur le fond :
- `dashboard/assets/page.tsx` + `api/v1/assets/route.ts` : liste générique multi-secteurs (Immobilier, Véhicule, Hôtellerie, Équipement), colonnes génériques (nom, secteur, statut, prix, vitrine, actions).
- `dashboard/assets/fleet/page.tsx` + `api/v1/assets/fleet/route.ts` : vue spécialisée **filtrée sur `assetType.sector === "VEHICLE"`** côté API (`fleet/route.ts:27`), avec des champs propres au secteur véhicule absents de la vue générique (immatriculation, marque/modèle/année, kilométrage, alertes d'expiration assurance/vignette à 30 jours, réservation active avec km de départ).

C'est donc une **fonctionnalité sectorielle distincte** (superset métier pour le secteur véhicule), pas un doublon de `dashboard/assets`.

**Constaté — page orpheline** : recherche exhaustive (`grep "assets/fleet"` sur tout `src/`) — le seul endroit qui référence l'URL `/dashboard/assets/fleet` ou l'endpoint `/api/v1/assets/fleet` est le fichier `fleet/page.tsx` lui-même (qui appelle son API) et le fichier de route API. **Aucun lien** dans `sidebar.tsx`, dans `dashboard/assets/page.tsx`, ni dans le dashboard KPI principal ne pointe vers cette page. Elle existe et fonctionne (si on tape l'URL directement) mais n'est accessible depuis aucun point d'entrée de navigation visible.

## 4. RTL / Dark mode / Responsive

**Dark mode (`next-themes`)**
- Constaté : `ThemeProvider`/`useTheme` est utilisé et le toggle clair/sombre est présent dans `src/components/dashboard/sidebar.tsx` (l.7, l.199-211).
- Constaté (recherche `dark:` sur `src/app`) : les classes `dark:` sont présentes dans 16 fichiers, tous situés sous `(dashboard)/dashboard/...` (calendar, settings, customers, bookings, contracts, assets — 350 occurrences au total), plus `error.tsx`, `not-found.tsx`, `loading.tsx` et le layout `(dashboard)`.
- Constaté : `src/app/(dashboard)/dashboard/page.tsx` (le tableau de bord KPI principal, première page vue après connexion) et `dashboard/analytics/page.tsx`, `dashboard/tickets/*`, `dashboard/assets/fleet/page.tsx` **ne contiennent aucune classe `dark:`** — si l'utilisateur bascule en mode sombre depuis la sidebar, ces écrans restent sur fond blanc/clair alors que le reste de l'interface passe en sombre.
- Constaté : **zéro** classe `dark:` dans tout `src/app/(portal)` et dans `src/components/portal/` (recherche vide sur les deux). Le portail client n'a donc aucun support dark mode, alors que le sélecteur de thème existe uniquement côté sidebar dashboard et n'est même pas exposé côté portail (`PortalSidebar` n'a pas de bouton thème).

**RTL (arabe)**
- Constaté : recherche `rtl:` sur tout `src/` → un seul fichier concerné, `src/components/dashboard/sidebar.tsx`, une seule occurrence (l.162, la barre indicatrice de lien actif). Aucune autre classe `rtl:` nulle part ailleurs dans l'application (ni dans les pages dashboard, ni portal, ni public, ni mon-espace).
- Le sélecteur de langue (FR/AR/EN) existe dans la sidebar dashboard (l.83-87, l.213-226) et pose un cookie `NEXT_LOCALE` avec rechargement de page, mais rien dans `Portalsidebar.tsx`, `(public)/layout.tsx` ni `mon-espace/layout.tsx` ne propose de changement de langue.
- **Hypothèse à vérifier** : le support RTL annoncé dans la documentation projet (classes Tailwind `rtl:`) semble être une intention de design system non implémentée dans les écrans, à l'exception d'un seul détail visuel dans la sidebar dashboard.

**Responsive**
- Constaté : `Portalsidebar.tsx` gère un layout responsive explicite à 3 états — sidebar desktop `hidden lg:flex` (l.47), header mobile `lg:hidden` (l.98), barre de navigation basse mobile `lg:hidden` (l.106-119).
- Constaté : `dashboard/sidebar.tsx` n'a pas d'équivalent mobile — c'est une sidebar fixe collapsible (largeur 72px/260px) sans breakpoint `lg:`/`md:` ni menu hamburger ; sur petit écran elle reste affichée en permanence, ce qui réduit fortement l'espace de contenu utile. **Constaté par absence** de toute classe responsive dans ce fichier.
- Constaté : `(public)/layout.tsx` et `mon-espace/layout.tsx` utilisent `hidden md:flex` pour masquer la nav horizontale sur mobile (l.19 et l.44 respectivement) sans proposer de menu de repli (pas de burger menu visible dans le code lu) — sur mobile, les liens de nav secondaire (`/agencies`, liens `mon-espace`) disparaissent purement et simplement.

## 5. Visibilité de navigation par rôle

- Constaté : `src/app/(dashboard)/layout.tsx` ne fait aucune vérification de session ni de rôle — il rend directement `<DashboardSidebar />` et les enfants (l.1-14).
- Constaté : `src/components/dashboard/sidebar.tsx` construit `navSections` comme un tableau statique (l.42-81), sans filtrage conditionnel sur `session.user.role`. Tous les rôles connectés au dashboard (ADMIN, MANAGER, OWNER...) voient donc exactement les mêmes entrées de menu, y compris celles pointant vers des pages inexistantes (`/dashboard/payments`, `/dashboard/invoices`, `/dashboard/maintenance`, `/dashboard/notifications`).
- Constaté : `src/app/(portal)/layout.tsx` vérifie uniquement la présence d'une session (`redirect("/auth/sign-in")` si absente, l.17-19) ; le commentaire du code lui-même indique explicitement "Le portail est accessible aux CLIENTs et aux autres rôles aussi (un ADMIN peut consulter le portail pour tester)" (l.21-22) — confirmation qu'il n'y a **aucune restriction de rôle** par design, pas seulement une omission.
- Constaté : `middleware.ts` (racine du projet) ne vérifie que la présence d'un cookie de session Better Auth pour les préfixes `/dashboard`, `/portal`, `/admin` (l.16-24) — aucune logique de rôle. Le matcher inclut `/admin/:path*` (l.30) alors qu'aucune page `/admin` n'existe sur le disque (route déjà confirmée absente) : c'est une protection de route pour un module qui n'a pas encore été construit.

**Conclusion section 5** : il n'existe, à ce stade, aucun mécanisme de visibilité de navigation ou de protection de route basé sur le rôle utilisateur (SUPER_ADMIN/ADMIN/MANAGER/OWNER/CLIENT) — ni au niveau des composants de nav, ni au niveau des layouts, ni au niveau du middleware. Seule l'authentification (session présente ou non) est vérifiée.
